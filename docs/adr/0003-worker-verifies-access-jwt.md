# 0003: The Worker verifies the Access JWT itself, with one verifier for every environment

Status: accepted (2026-10-08)

## Context

In production Cloudflare Access sits in front of the whole hostname, but authorization has to be enforced by the application, not only by the edge. Local development and the test suite have no Cloudflare account, and a separate "dev auth" path (for example a header naming the user) would mean the production check is never exercised before deploy.

## Decision

`JwtIdentityVerifier` (`src/worker/auth/identity.ts`) verifies RS256 tokens with jose: signature, issuer, audience, expiry, `iat`, and `sub` for users. It has two key sources and one code path. Production uses `createRemoteJWKSet` on `<team domain>/cdn-cgi/access/certs` and reads only the `Cf-Access-Jwt-Assertion` header. Dev and tests use a local JWK set generated by `npm run dev:keys`, with tokens minted in the Access claim shape by `/dev/token`. The verified identity is mapped to an employee and role in D1; request bodies never carry identity. `/dev/*` routes exist only in dev mode, and dev mode answers 500 `misconfigured_auth_mode` on any hostname other than `localhost`, `127.0.0.1` or `[::1]`, so an accidental production deploy in dev mode fails closed.

## Consequences

- The production key path is tested offline: the `worker-access` Vitest project serves a JWK set through `outboundService` for `https://team.test/cdn-cgi/access/certs`.
- Real Access has not been exercised until the owner deploys; until then the honest claim is Access-compatible JWT verification, tested offline.
- Service tokens need a Service Auth policy on the Access application, and their JWT names the token by its Client ID in `common_name` (ADR 0005).

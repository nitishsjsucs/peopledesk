# 0003: The Worker verifies the Access JWT itself, with one verifier for every environment

Status: accepted (2026-10-08)

## Context

In production Cloudflare Access sits in front of the whole hostname, but authorization has to be enforced by the application, not only by the edge. Local development and the test suite have no Cloudflare account, and a separate "dev auth" path (for example a header naming the user) would mean the production check is never exercised before deploy.

## Decision

`JwtIdentityVerifier` (`src/worker/auth/identity.ts`) verifies RS256 tokens with jose: signature, issuer, audience, expiry, `iat`, and `sub` for users. It has two key sources and one code path. Production uses `createRemoteJWKSet` on `<team domain>/cdn-cgi/access/certs` and reads only the `Cf-Access-Jwt-Assertion` header. Dev and tests use a local JWK set generated by `npm run dev:keys`, with tokens minted in the Access claim shape by `/dev/token`. The verified identity is mapped to an employee and role in D1; request bodies never carry identity. `/dev/*` routes exist only in dev mode, and dev mode answers 500 `misconfigured_auth_mode` on any hostname other than `localhost`, `127.0.0.1` or `[::1]`, so an accidental production deploy in dev mode fails closed. That hostname comes from the Host header, which a client can set, so the local dev and preview servers also refuse connections from any non-loopback address (`scripts/lib/loopback-only.ts`); without that, a dev server started with `--host` would mint tokens for anyone on the network who sent `Host: localhost`.

## Consequences

- The production key path is tested offline: the `worker-access` Vitest project serves a JWK set through `outboundService` for `https://team.test/cdn-cgi/access/certs`.
- Real Access was not exercised before the deploy on 2026-10-15, so until then the honest claim was Access-compatible JWT verification, tested offline. Since 2026-10-15 real Access sits in front of production, and the Worker has verified its JWTs on service-token requests during eval windows (`verify:production`, the `/mcp` checks of `verify:ai-search` and the 20-case production eval; README, Production setup). A user sign-in with a One-time PIN has no recorded production check yet.
- Service tokens need a Service Auth policy on the Access application, and their JWT names the token by its Client ID in `common_name` (ADR 0005).
